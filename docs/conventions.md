# Conventions — match-padel-api

## Naming

| Thing | Convention | Example |
|---|---|---|
| Files | kebab-case | `match.service.ts` |
| Classes | PascalCase | `MatchService` |
| Functions / methods | camelCase | `findActiveMatches()` |
| Variables | camelCase | `activeMatch` |
| Global constants | UPPER_SNAKE | `MAX_PLAYERS_PER_MATCH` |
| DB tables (reference) | snake_case | `court_reservations` |
| HTTP routes | kebab-case | `/club-staff/:clubId` |
| Error codes | UPPER_SNAKE | `MATCH_NOT_FOUND` |

## Domain structure — required files

Each domain MUST have exactly these 5 files (plus the `__tests__/` folder):

```
domains/matches/
├── match.router.ts
├── match.controller.ts
├── match.service.ts
├── match.repository.ts
├── match.validator.ts
└── __tests__/          (target — not implemented yet; see 'Real state vs. target' in CLAUDE.md)
    └── match.test.ts
```

File names use the singular entity name (`match.router.ts`) inside the plural directory, with the suffixes `.router.ts`, `.controller.ts`, `.service.ts`, `.repository.ts` and `.validator.ts`. The plural files (`matches.router.ts`, etc.) are unused empty stubs; do not create new ones. Not every domain has all five files today; see the inventory in `docs/endpoints.md`.

Do not create extra files unless they are specific workers (`match.elo-worker.ts` (target — not implemented yet; see 'Real state vs. target' in CLAUDE.md)).

## Types

- Supabase table types come from `src/types/supabase.ts` (autogenerated with `supabase gen types typescript`) (target — not implemented yet; see 'Real state vs. target' in CLAUDE.md)
- Request/response types are defined in `match.validator.ts` as Zod inference: `type CreateMatchInput = z.infer<typeof createMatchSchema>`
- **Never** hand-write `interface Match { id: string; ... }` if the type exists in supabase.ts (until the file exists, existing repositories declare local interfaces; do not copy that)

## Validators (Zod)

Define schemas in `<domain>.validator.ts` and export them. The controller imports and uses them (today only `auth` and `reservations` have a validator file; other controllers define their schemas inline or do not validate yet):

```typescript
// match.validator.ts
export const createMatchSchema = z.object({
  clubId: z.string().uuid(),
  courtId: z.string().uuid(),
  startTime: z.string().datetime(),
  minCategory: z.enum(['1', '2', '3', '4', '5', '6', '7']),
})
export type CreateMatchInput = z.infer<typeof createMatchSchema>

// match.controller.ts
const input = createMatchSchema.safeParse(req.body)
if (!input.success) {
  return res.status(400).json({
    success: false,
    error: { code: 'VALIDATION_ERROR', message: 'Invalid input', details: input.error.flatten() }
  })
}
```

## Errors

Always use the envelope format. The error classes live in `src/types/errors.ts`. `AppError` takes `(message, statusCode = 500, code?)`:

```typescript
throw new AppError('The match does not exist', 404, 'MATCH_NOT_FOUND')
```

Subclasses that exist today: `NotFoundError(resource)`, `UnauthorizedError(message)`, `ForbiddenError(message)`, `ConflictError(message)`, `ValidationError(message)`, with the codes `NOT_FOUND`, `UNAUTHORIZED`, `FORBIDDEN`, `CONFLICT`, `VALIDATION_ERROR`.

The global `errorHandler` (`src/middleware/error.middleware.ts`) catches it and builds the response. Note: the mounted handler currently responds with the legacy shape `{ error, message }` instead of the envelope; the duplicate `src/middleware/error.ts` has the envelope version. New code must still target the envelope.

## Logging

```typescript
import { logger } from '../../lib/logger'

logger.info({ matchId, userId }, 'Score accepted')
logger.error({ err, matchId }, 'ELO calculation failed')
```

Always pass context as the first argument (object), message as the second. `src/lib/logger.ts` exists but is a thin `console` wrapper and is not structured JSON yet (structured JSON to stdout (target — not implemented yet; see 'Real state vs. target' in CLAUDE.md)).

## Imports

Use path aliases defined in `tsconfig.json` (target — not implemented yet; see 'Real state vs. target' in CLAUDE.md) (`tsconfig.json` has no `paths` today and all code uses relative imports; until the aliases are configured, use relative imports):
- `@/domains/...`
- `@/middleware/...`
- `@/lib/...`
- `@/types/...`

Do not use relative paths like `../../..`.

## HTTP Status codes

| Situation | Status |
|---|---|
| Success with data | 200 |
| Successful creation | 201 |
| Validation failed | 400 |
| Not authenticated | 401 |
| No permissions | 403 |
| Not found | 404 |
| Conflict (already exists) | 409 |
| Internal error | 500 |

## Environment variables

Always access via `process.env.NAME`. If it is required and missing, the process must fail on startup (validate in `src/lib/config.ts` (target — not implemented yet; see 'Real state vs. target' in CLAUDE.md); today only `src/lib/supabase.ts` fails on startup when `SUPABASE_URL` or `SUPABASE_SERVICE_ROLE_KEY` is missing).
